## Requirement understanding

One line: Don wants a production/triggered agent run to be unable to change the agent's own configuration (connector tool switches, permissions and approval rules, triggers, evaluation rules, SOP/skill content, model settings) — only the agent's own chat (builder/maintenance) may change it, and "Run now" / "Run for…" and the public API count as production runs too, per Micus's 2026-10-26 decision.

Don (reporter) observed that every agent now carries the system MCP `mspbots-agent`, exposing platform admin tools such as `upsert_agent_permissions`, and reasoned that a running agent could use these to defeat its own safety controls (e.g. re-enable a tool a human just switched off). PRD-17198 (closed 2026-09-03) does not cover this: its premise — "no agent has the platform's admin API in its tool list" — no longer holds.

Decisions recorded on the ticket (Micus, 2026-10-26): (a) always on for every agent, no per-agent/per-trigger switch in v1; (b) "Run now" and "Run for…" count as production runs and are refused too; only the agent's own chat may change configuration. Scope and Done when are final for dev (not subject to further product review).

## Product design

### Goals / Non-goals

**Goals**
- A production/triggered agent run cannot change its own configuration: connector tool switches, permissions, approval rules, triggers, evaluation rules, SOP/skill content, and model settings.
- A refused attempt returns a clear, specific tool error and leaves the configuration unchanged.
- The agent's own chat (interactive chat + the SOP Author builder/maintenance session) is unaffected — an owner/admin can still change all of the above there.

**Non-goals (v1, per the ticket)**
- No per-agent or per-trigger on/off switch — the rule is always on for every agent.
- No visible "build vs production" mode (planned later, alongside Epic PRD-20763's draft/live per client).
- Restricting chat itself to admins is out of scope.
- `mspbotsagent_run_trigger` (executing an existing trigger) is not restricted — it is an action, not a configuration change.

### Acceptance criteria AC1..AC6

- **AC1** — In a form- or schedule-triggered run, the connector tool-switch route (`set_connector_tools` / `PUT /api/agents/:id/connectors/:cid/tools`) is refused and the agent's tool switches are unchanged afterward. *(Given/When/Then: given a task-origin run, when a call tries to flip a connector tool switch, then the call is refused and `.mcp.json`'s `allowedTools`/`disabledTools` are unchanged.)*
- **AC2** — `upsert_agent_permissions` is refused the same way in such a run.
- **AC3** — Each other category in scope (triggers, evaluation rules, SOP/skill content, model settings) has at least one refused call verified. `run_trigger` is explicitly verified as *not* refused (it executes, it does not configure).
- **AC4** — A tool switched off by a person stays off for the next run, even if a triggered run tried to switch it on.
- **AC5** — In the agent's own chat (interactive) and in the SOP Author builder/maintenance session, an owner/admin can still change the same settings — unaffected by this change.
- **AC6** — Every refused attempt shows in the run's history (as a tool-call error in the run/thread transcript).

### Open questions

- **OQ1 (non-blocking, assumption applied):** `RunOrigin` declares `"test"` and `"compact"` but no call site setting either was found in this repo at the inspected sha (`"compact"` is set client-side only, `components/assistant-ui/aegra/compact.ts:23`, for LangGraph's own history-compaction call — not a user-driven run). Assumption: only `origin ∈ {chat, build}` is exempt; `test`/`compact`/anything unrecognized is treated as non-exempt (fail closed). If a future "test this agent" feature sets `origin: "test"` from inside the builder, it should be added to the exempt set then.
- **OQ2 (non-blocking):** Connector tool switches and model settings have no current agent-callable MCP tool (see Current state). The design still gates both backend routes for defense-in-depth. AC3's test for these two categories exercises the route directly (api-key + non-exempt `X-Run-Origin`), not via a literal tool call, since none exists yet.
- **OQ3 (non-blocking, defensive test added as TC15):** Whether any frontend caller of `POST /api/agents/:id/run[/wait]` ever sends `body.source === "chat"` (which would make the derived `origin` resolve to `"chat"` and wrongly exempt a "Run now"/"Run for…" call) was checked across this repo's `components/` tree and no such call site was found. Not blocking; defended by TC15 (fail-closed on anything not exactly `chat`/`build`) regardless.

## Tech design

### Conclusion

Enforce the refusal **inside `mb-platform-agent`'s backend routes** (not in `mb-platform-agentos`'s tool-call layer), gated on a new signal — the run's `origin`, already captured but currently dropped before it leaves `mb-platform-agent` — threaded through `mb-platform-agentos` and `mspbots-agent-mcp` as a forwarded header. No existing field's semantics (`source`, `run_source`) are changed.

### Where the current implementation lives

See the Current state tables above for every route, file, and line. Summary of the three repos' roles is in "Multi-repo span".

### Option analysis

**Option A — reuse the existing coarse `run_source` ("task"/"chat"), fix the two mis-tagged entry points.** `mb-platform-agentos`'s `graph.py:39` (`_writable`) already reads `run_source` this way, so this would be the smallest diff: retag `triggerRun` (route.ts:1254) and `agent-invoke.ts:66` from `source: "chat"` to `source: "task"`, then gate on `run_source == "task"`.
Rejected: `source` already has two independent consumers that are not part of this ticket and would change behavior as a side effect — `listAllRuns`'s "All runs" / Inbox page filters by `source: "task"` (`route.ts:1739,1767`), so "Run now"/"Run for…"/public-API runs would start appearing there, where they do not today; and `_writable` itself would newly make those runs' filesystem read-only. Both may well be *desirable* (these genuinely are non-chat runs), but they are visible, user-facing side effects outside this ticket's stated scope, and no amount of care in this ticket's own tests would catch a regression in a filter this ticket never touches.

**Option B — chosen.** Thread the already-finer `origin` field through as a new, additive piece of context, independent of `source`/`run_source`:
1. `mb-platform-agent`'s `runContext()` additionally emits `run_origin` (from the existing `origin` already recorded in run metadata) — a one-line addition, `source`/`run_source` untouched.
2. `mb-platform-agentos` reads `configurable.run_origin` in `make_graph()` and passes it down to where MCP tool calls are built, which already injects per-call headers for an unrelated purpose (`agent_id`/`thread_id` auto-fill, see below) — the same mechanism gets a third header.
3. `mspbots-agent-mcp` reads that one extra header and forwards it, unchanged, to `mb-platform-agent`.
4. `mb-platform-agent`'s configuration-changing routes check it.

Zero side effects on `source`/`run_source` consumers; the diff in `mb-platform-agentos` and `mspbots-agent-mcp` is ~2 files each, both repos having an established, directly analogous pattern to extend (the `_caller` interceptor; the three-header auth middleware) rather than inventing a new one.

### Data & API contract

- New header, agentos → `mspbots-agent-mcp`: `X-Channel-Run-Origin: <origin>` (matches that repo's own `X-Channel-*` naming convention).
- New header, `mspbots-agent-mcp` → `mb-platform-agent`: `X-Run-Origin: <origin>` (matches `mb-platform-agent`'s own header style for this kind of internal signal).
- Exempt values: `chat`, `build`. Anything else (including absent) ⇒ refused when the caller is api-key-authenticated.
- Refusal response: `403`, JSON envelope `{ "success": false, "error": "This agent's configuration can't be changed during a triggered run" }` — this exact string is what `AgentClient`'s `AgentError.to_envelope()` (`mspbots-agent-mcp/src/mspbots_agent_mcp/api_client.py:56-67`) will relay back as the MCP tool call's error result, satisfying "a refused call returns a clear tool error" without new code in the MCP layer.
- No DB schema change. No migration.

### Key flow / sequence

```
schedule/event/webhook/Run-now/public-API starts a run
  → mb-platform-agent tags origin (cron/manual/event/api — all already correct, see Current state table)
  → runMetadata() records it; runContext() now also emits run_origin (NEW)
  → Aegra configurable.run_origin reaches mb-platform-agentos's make_graph()
  → agentos passes run_origin into mcp.load() → tools() → _caller()
  → every MCP tool call agentos makes now carries X-Channel-Run-Origin
  → mspbots-agent-mcp's server.py reads it, forwards as X-Run-Origin
  → mb-platform-agent's guard sees X-Run-Origin != chat/build on an api-key call
    to a configuration-changing route → 403, config unchanged
  → the MCP tool call returns an error envelope → visible in the run's transcript (AC6)
```

Chat / builder path: identical, except `origin` is `chat`/`build` throughout, so the guard's `null`-return path keeps every current write working unchanged (AC5).

### Non-functional

- **Multi-tenancy**: the new header carries only `origin`, never tenant/identity data; existing per-tenant scoping (`requireAgentAccess`, schema-per-tenant DB access) runs first and is untouched — see TC14. No new cross-tenant surface.
- **Fail-closed by design**: missing or unrecognized `X-Run-Origin` on an api-key call is treated as production (refused), not allowed — see TC15. This is the one non-functional property load-bearing enough to call out: it means a **rollout-order risk** exists (next bullet).
- **Rollout order (hard requirement, not a suggestion)**: because the header is fail-closed, if `mb-platform-agent`'s guard goes live *before* `mb-platform-agentos` and `mspbots-agent-mcp` are both sending it, **every** api-key-authenticated agent self-configuration call — including legitimate ones made from the agent's own chat/build session — would start being refused (the header would simply be absent). Deploy order: (1) `mspbots-agent-mcp` + `mb-platform-agentos` changes first, confirm (via logs) that `X-Run-Origin` is arriving with the correct value for at least one real chat/build session and one real triggered run; (2) only then deploy `mb-platform-agent`'s guard. This is an explicit instruction for the dev leg's Rollout & rollback section, not optional sequencing.
- **Concurrency**: no new write path; the guard is a pure read-and-reject before the existing handler runs, so it does not change any existing locking/partial-write behavior (e.g. the agent-policy "don't write concurrently" note in `mspbots-agent-mcp/README.md`).
- **Observability**: the refusal itself is visible in run history (AC6) by construction (tool-call error), so no new logging is strictly required, but the dev leg should consider a log line on refusal (agent id, route, origin) for abuse/monitoring purposes — not a blocking requirement.

### Rollout & rollback

- No feature flag (none requested, none exists in this codebase for this kind of gate). Always-on per the ticket's own scope.
- Rollback is a plain revert of the three repos' changes; no data was written, so no backward migration is needed.
- See the rollout-order requirement under Non-functional — it is the only ordering constraint.

- `mb-platform-agentos`: ~0.5 day (signature threading through 3 functions, 1 new header constant, tests).
- `mspbots-agent-mcp`: ~0.5 day (middleware + client header, tests).
- Suggested sub-tasks: one per repo, in the rollout order above (agentos + mcp first, agent last).

### Risks & dependencies

- **Rollout-order risk** — see Non-functional; the dominant risk in this design.
- **Coordination risk**: 3 repos must ship in the stated order; if `mb-platform-agent`'s guard is cherry-picked/merged ahead of the other two by mistake, every triggered run's legitimate self-configuration calls would start failing loudly (not silently) — fail-closed means the failure mode is visible, not a silent security hole, which is the safer direction to err in.
- **No dependency on any other open ticket.** PRD-20279 (sibling bug, same repo) is unrelated in effect but was the source of the (partially incorrect) `set_connector_tools`-is-an-MCP-tool claim this design corrected.
