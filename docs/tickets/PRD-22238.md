## Requirement understanding

One line: Felix wants the three MSPbots Agent Platform MCP save tools (upsert_agent_approval, upsert_agent_permissions, upsert_agent_evaluation) to stop returning big objects, including the full system prompt, and return only the key information that tells the agent the save worked.

Reporter's answer (2026-11-16): a successful save returns only the saved object's id, a success flag and the updated timestamp - no system prompt, no full agent object, no other fields. Owning repo: mspbots-agent-mcp. Scope (triage): only these three tools; get tools and all other tools unchanged; the platform's `PUT /api/agents/:id` response must not change (the UI uses it).

## Current state (every claim carries path:line)

- The three tools share one partial `PUT /api/agents/:id` and end with `return dump_json(result)`, i.e. the platform's whole answer: `agents.py:371-374` (permissions), `agents.py:459-463` (evaluation), `agents.py:497-503` (approval). The comment at `agents.py:11-15` says the same.
- What the platform answers: `ok({...toDto(row), steps, toolCallLimit, recursionLimit, permission, permissionEffective})` = `{success: true, data: <whole agent>}` (`mb-platform-agent service/agent/route.ts:1164-1172`; `ok` at `service/common/envelope.ts:16`). `toDto` carries `id` (`dto.ts:13`), the agent prompt and `updatedAt` (`dto.ts:51-53`). That is why the full system prompt comes back.
- `dump_json` is deliberately not size-capped (`_json.py` docstring), so nothing trims it later.
- Failures: HTTP >= 400 raises `AgentError` -> `e.to_envelope()` (`api_client.py:_handle`), already small. `docs/modules/mcp-tools.md` records that some platform endpoints answer HTTP 200 with `success:false`; this one's `fail(...)` branches (e.g. "Agent not found", `route.ts:674`) may do the same, so a `success:false` body must be passed through untouched.
- Pre-checks that return early (`_rules_missing_rubric` -> `error_envelope`, `_invalid_bare_tool_ids`, `_guard_policy`, `NO_TOKEN`) are not touched.
- Reference for the tool-side shaping style: `tools/usage.py` (shape the upstream answer inside the tool, not in `_json`).
- Reproduction: the report says "call any of the three tools"; the code path above shows the full `toDto` record is returned on every successful call. Not re-run live: vendor MCP tickets do not require live repro, and the three tools write to a live agent (see Open questions).

## Product design

### Goals
1. A successful call of each of the three tools returns a small acknowledgement: `{"success": true, "id": "<agent id>", "updatedAt": "<ISO timestamp>"}` - and nothing else.
2. The saved values are unchanged: only the response shrinks. The matching get tool returns what was just saved.
3. Errors keep their current shape and text.

### Non-goals
- No change to the get tools, `update_agent`, or any other tool.
- No change to what mb-platform-agent's `PUT /api/agents/:id` returns (the UI depends on it); no platform change at all.
- No new tool, parameter or option (no `verbose` switch).

### Acceptance criteria
- AC1 (DW1): Given a valid approval rules payload, When `mspbotsagent_upsert_agent_approval` is called, Then the response is exactly `{"success":true,"id":<agent id>,"updatedAt":<timestamp>}` with no system prompt and no other agent field.
- AC2 (DW2): Same for `mspbotsagent_upsert_agent_permissions`.
- AC3 (DW3): Same for `mspbotsagent_upsert_agent_evaluation`.
- AC4 (DW4): Given a save succeeded, When the matching get tool (`get_agent_approval` / `get_agent_permissions` / `get_agent_evaluation`) is called, Then it returns the values just saved.
- AC5 (DW5): Given an invalid payload or a platform refusal, When a save tool is called, Then it returns the same error message as before this change.
- AC6 (DW6): Given the same test agent, When each of the three tools is called successfully, Then each response is under 1 KB.

### Open Questions
1. `permissionEffective` (when a permission change takes effect, added by PRD-21874) used to be in the `upsert_agent_permissions` response and is now dropped, per the reporter's "no other fields". Does not block implementation; assumption: acceptable, the agent re-reads with `get_agent_permissions` if it cares. If product wants it kept, it is one extra key and AC2 changes.
2. If the platform answer has no `updatedAt`, the ack carries `"updatedAt": null` rather than omitting the key. Does not block; assumption stated here.
3. Live reproduction on production was not run: it would require saving to a real agent (SOPs 1158-1160 are the reporter's). Does not block; the code path proves the behaviour.

## Technical design

### Change list
- `src/mspbots_agent_mcp/tools/agents.py` [change] - add one helper `_save_ack(result, agent_id)`: if `result` is a dict with `success is True` and a dict `data`, return `{"success": True, "id": data.get("id") or agent_id, "updatedAt": data.get("updatedAt")}`; for anything else (including `success is False`, `None`) return `result` unchanged. In the three tools replace `return dump_json(result)` with `return dump_json(_save_ack(result, agent_id))`. Update the three docstrings: "Returns the updated agent record as JSON" (permissions) becomes "Returns {success, id, updatedAt} only; call the matching get tool to see the saved values"; evaluation and approval docstrings get the same one-line statement. Update the shared comment block at the top (lines 11-15) to mention that save responses are acknowledgements only.
- `README.md` [change] - lines 205, 207, 209: add "Returns `{success, id, updatedAt}`" to the three rows.
- `tests/test_tools.py` [change] - new tests (see Test cases); stub clients return a realistic big platform answer.
- `docs/modules/mcp-tools.md` [not written by design] - the dev leg updates it after delivery.

### Contract
Success response (all three tools):
```
{"success":true,"id":"a1","updatedAt":"2026-11-16T10:00:00.000Z"}
```
Request, error envelopes, tool names, input schemas and annotations are unchanged. Platform call unchanged (`PUT /api/agents/:id` with the same bodies).

### Options
No alternative worth a table: trimming at the platform route would change what the UI receives (explicitly forbidden by triage), and a global trim in `dump_json` would also shrink the get tools (out of scope). One shared helper in the tool layer is the smallest change and the repo's existing style (`usage.py` shapes upstream answers in the tool).

### Reuse and cleanup
- Reuse: `dump_json` (`_json.py`), the existing `result.get("success") is False` convention (`agents.py:617`, `connectors.py:169`). No new dependency.
- New signature: `_save_ack(result: Any, agent_id: str) -> Any` (module-private).
- Cleanup in touched code: none needed.
- Suggested separate tickets: `mspbotsagent_update_agent` also returns the whole agent (`agents.py:~622`); out of scope here (triage: only the three tools), worth a follow-up.

### Non-functional
- Idempotency/concurrency: unchanged; the PUT and the "do not call two at once" warning stay.
- Performance: response shrinks from the whole agent (prompt-sized) to under 200 bytes; no extra request.
- Security: removes the system prompt from MCP responses; no new data exposed. No credential handling changed.
- Multi-tenancy: unchanged (tenant header logic in `api_client.py`).
- Observability: none added.

### Testing strategy and regression surface
Unit tests with stub clients (pattern of `tests/test_tools.py:431`). Regression surface: the three tools' success text only; existing tests that assert on the PUT body keep passing. Run `uv run pytest`.

### Release order
No dependency: a single repo, MCP side only. Existing callers that read fields from the old response (the model reading the agent record from the save response) are told in the docstring to use the get tool.

### Effort & breakdown
Story points: 1
Tier: one connector, several related fixes in one repo (row "1")
Considerations: 1 module; modifies existing code; no external API; no destructive writes; no migration; no UI; 6 acceptance scenarios, all unit-testable with stubs
Main uncertainty: the exact platform answer shape on a platform refusal sent as HTTP 200 (handled by passing it through unchanged)
Order inside this ticket: 1) helper + three call sites 2) docstrings and README 3) tests

### Risks
- A caller that parsed the old full record from the save response loses it. Mitigated by the docstring and the get tools; this is the requested behaviour.
