## Requirement understanding

In one sentence: wrap the overview endpoint behind the Usage page (per-agent spend/run counts, plus the creator's email and creation time) as a read-only tool under the MSPbots Agent Platform MCP.

Restated: the reporter has already written out the full interface contract (`GET /api/usage/overview`, 7 optional query parameters, the full 200 response shape,
two error cases, and the suggested tool name `mspbotsagent_get_usage_overview`). The job is to add a 1:1 wrapper tool in this repo:
forward the caller's `Authorization`, pass the parameters through unchanged, and hand the response JSON back to the model; `debug` may be stripped,
but `spendUnavailable` / `spendTruncated` must be passed through as-is. Success looks like: an agent can answer
"how much did we spend this week, which agent spent the most, who created these agents", and says "unavailable" instead of "0" when spend cannot be read.

## Current state (every assertion carries path:line)

### 1. This repo already solves the three things the ticket worries about

The ticket stresses three points for wrappers; checked one by one, all are already existing behavior (read at `e45ded6`):

1. **Mount prefix** - the ticket says an external wrapper must use "the deployment origin + the `/apps/{app}/` prefix".
   `src/mspbots_agent_mcp/api_client.py:13` has `_APP_PREFIX = "/apps/mb-platform-agent"`,
   `:83` builds `_base_url` with `host.rstrip("/") + _APP_PREFIX`, and `:123` appends the `path` passed in.
   **The tool only needs to write `/api/usage/overview`.**
2. **Forward the caller's token** - `api_client.py:87` always sends `Authorization: Bearer {self._token}`,
   and the token comes from the contextvar isolation in `server.py` (`client_factory` from `server.py:83`), one credential per call.
   **The "forward as-is, no service account" required by AC4 already holds**; nothing needs to be done for it in this ticket.
3. **Invalid values fall back to defaults** - `_clean_params` at `api_client.py:93-96` drops any parameter whose value is `None`.
   So the wrapper **does not send** unspecified parameters and the server picks its own defaults. **AC3's "fall back instead of error" holds naturally**;
   there is no need to rewrite the validation in the wrapper (rewriting would instead drift from the server's rules).

### 2. The way tools are written in this repo is settled

`src/mspbots_agent_mcp/tools/connectors.py` is the closest template for this ticket (read-only, zero parameters, one GET):

- Each module exports `register(mcp, client_factory)`; `server.py:118` has a one-line import and `:120-125` a one-line call.
- Read-only tools are marked `@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))` (`connectors.py:13`).
- When no credential is available, return `_common.NO_TOKEN` (`tools/_common.py`, an error envelope of `not_configured`).
- Upstream errors go through `except AgentError as e: return e.to_envelope()` (`api_client.py:62-64`, classified by status code and marked retryable).
- Return values use `_json.dump_json_capped(...)`.

### 3. Two traps the design must handle (newly found in this ticket)

**Trap 1 - output has a 20000-character cap, while `pageSize` can be up to 1000.**
`MAX_CHARS = 20_000` at `_json.py:11`; when over the limit `dump_json_capped` **truncates the largest list field**
(`_json.py:18-30`). A `breakdown` row of this endpoint has 10 fields, so with `pageSize=1000` it easily exceeds 20k characters -
**some rows are silently cut off while `breakdownTotal` still reports the full count**, and the model would think it has seen everything.
This is the only place in this ticket where the wrapper needs extra logic; see Technical design item 3.

**Trap 2 - the UI says "credits", the API says "USD".**
`ProductDocs/16-Usage.md:29` records that the KPI tiles are **CREDITS USED / TASKS**, quote: "Spend is denominated in credits";
`:31` records that the Breakdown columns are **AGENT / MODEL LAST USED / CREDITS / TASKS** (_verified_ 2026-08-12, v4.1.292).
The ticket's response contract, however, says `totalSpend` (USD), `cost` (USD), `runs`. The same data is called credits in the UI and
USD in the API; the UI's TASKS corresponds to the API's `runs`; the API also returns `threads`, which **no longer has a tile** in the UI
(`16-Usage.md:29`: the THREADS tile was removed in v4.1.408).

**Why this matters**: the tool's `description` is read by the model. If it says "total spend (USD)", the model will answer
"you spent 12.34 dollars", while the user sees "185.06 credits" on the Usage page - the two numbers do not match and the user will treat it as a bug.
For handling see OQ-1 (proceeding on an assumption, not blocking).

## Product design

### Goals

- **G1** An agent can ask in natural language about the tenant's usage: total spend, run count and agent count over a period,
  a per-agent breakdown (spend/runs/model), and each agent's creator and creation time.
- **G2** When spend cannot be read, the agent can say "unavailable" instead of reporting 0.
- **G3** Data is returned strictly for the caller's own tenant, with no cross-tenant leakage.

### Non-goals

- **N1 No drill-down for a single agent via `GET /api/usage/agent/{agentId}/runs`** (the ticket explicitly puts it out of scope;
  it could later be a second tool, `mspbotsagent_get_agent_usage_runs`).
- **N2 No change to mb-platform-agent** - the endpoint already exists, this ticket only wraps it (the ticket's own words).
- **N3 The wrapper does not recompute or correct any value** (no USD<->credits conversion, see OQ-1): the wrapper either passes through as-is
  or states it explicitly, and never calculates on its own - a wrongly computed number is far worse than no computation.

### Acceptance criteria

**AC1** Given the MSPbots Agent Platform MCP has this change loaded, When tools are listed,
Then there is a tool whose name has the `mspbotsagent_` prefix and expresses the `usage_overview` intent,
annotated read-only (`readOnlyHint`), with no required parameters.

**AC2** Given a caller with a valid platform token, When the tool is called without any parameters,
Then the returned JSON matches the response of `GET /api/usage/overview` for the same user (default `7d` / page 1 / 10 rows / cost desc).

**AC3** Given the same caller, When `range` / `page` / `pageSize` / `sortBy` / `sortOrder` / `sopId` / `source` are passed one at a time,
Then each parameter is forwarded and the result visibly changes; when invalid values are passed (such as `range=xx`, `sopId=-1`) there is **no error**,
and it falls back to the server default.

**AC4** Given no credentials are provided, When the tool is called, Then it returns a `not_configured` error envelope;
Given an invalid token, Then it returns the envelope corresponding to the upstream `401 UNAUTHENTICATED`, **not** the wrapper's own generic error.

**AC5** Given the target deployment contains mb-platform-agent commit `08745928`, When the tool is called,
Then every row of `breakdown[]` carries `createdBy` (an email, or the raw UUID when it cannot be resolved) and `createdAt` (an ISO string or `null`),
and for rows with `deleted: true` both fields are `null`.

**AC6** Given the upstream returns `spendUnavailable: true` or `spendTruncated: true`, When the tool is called,
Then these two booleans **appear as-is** in the tool's return value (not rewritten, not swallowed).

**AC7 (added in this ticket, for Trap 1)** Given `pageSize` is large enough that the response exceeds the output cap, When the tool is called,
Then the return value **must not** be in the state "rows are quietly cut off but `breakdownTotal` still reports the full count":
either the rows are complete, or the return value has an explicit marker saying how many rows were truncated.

**AC8 (added in this ticket)** Given the upstream returns a `debug` field, When the tool is called,
Then the return value has no `debug` (stripped as the ticket suggests), and none of the other fields is missing.

### Open Questions

- **OQ-1 (proceeding on an assumption, not blocking) - how to word the monetary unit in the tool description.**
  The API says USD, the UI says credits (`16-Usage.md:29`, _verified_ 2026-08-25).
  **Assumption of this design**: field names always keep the API's original names (`totalSpend` / `cost`), and the tool `description` states explicitly
  "values come from the same source as the CREDITS column of the Usage page, which is priced in credits", with **no conversion at all** (N3).
  If Product requires the tool to report credits directly, the authoritative source of the conversion rate must be confirmed first - and then the return-value section of the technical design has to be redone.
- **OQ-2 (not blocking) - whether to keep `threads`.** The API returns it, but the UI removed the THREADS tile in v4.1.408.
  Assumption: **pass through as-is** (one more field does no harm to the model, and removing it could make questions like "how many conversations" unanswerable).
- **OQ-3 (must be answered, but it is about the environment, not the code) - the verification environment for AC5.**
  `08745928` is on the `kaka-new-thread` branch of mb-platform-agent. **First confirm it has reached the deployment the MCP container actually calls**
  (`release-aks` / `INT`); otherwise `createdBy` / `createdAt` do not exist in the response at all and AC5 cannot be judged.
  This does not block design or implementation, but it **blocks acceptance of AC5**.

## Technical design

### Change list

1. **Add `src/mspbots_agent_mcp/tools/usage.py`** - following the shape of `tools/connectors.py`:
   ```python
   def register(mcp: FastMCP, client_factory: Callable[[], AgentClient | None]) -> None:
       @mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
       async def mspbotsagent_get_usage_overview(
           range: str | None = None, page: int | None = None, pageSize: int | None = None,
           sortBy: str | None = None, sortOrder: str | None = None,
           sopId: int | None = None, source: str | None = None,
       ) -> str:
   ```
   All parameters **default to `None`** (rather than being given default values) - so that `_clean_params` (`api_client.py:93-96`) drops the unset ones entirely,
   the server uses its own defaults, and the fallback semantics of AC3 are held only by the server.
   Function body: `client = client_factory()`; if `None` -> `return NO_TOKEN`;
   `await client.get("/api/usage/overview", params={...})`;
   `except AgentError as e: return e.to_envelope()`; on success process per item 3 and then `dump_json_capped`.
   **The docstring is read by the model**, so write it in the repo's style as "when to use it" plus key semantics (pagination is per agent not per time,
   `range=all` has no `daily`, when `spendUnavailable=true` you must say it is unavailable, `createdBy` may be a UUID rather than an email,
   and the credits note from OQ-1).
2. **`src/mspbots_agent_mcp/server.py:118` and `:120-125`** - add one line each for the `usage` import and register.
3. **Return-value shaping (the only logic of our own in this ticket, for Trap 1 and AC7/AC8)**:
   - Strip `debug` (AC8).
   - **Decide before handing to `dump_json_capped`**: if the serialized result would exceed `_json.MAX_CHARS`,
     proactively truncate `breakdown` to the number of rows that fit, and add two fields: `breakdownReturned: <actual row count>` and
     `breakdownTruncatedByToolOutput: true`. **Do not rely on the default truncation of `dump_json_capped`** -
     it silently chops rows and leaves no marker (`_json.py:18-30`), which is exactly the state AC7 forbids.
     (The alternative is to hard-cap `pageSize` in the wrapper to a value that fits, but that would make AC3 "parameters forwarded as-is" untrue,
     so we chose "forward as given, and mark explicitly if exceeded".)
4. **`tests/test_tools.py`** - add a line to `EXPECTED_TOOLS`:
   `"mspbotsagent_get_usage_overview": (set(), {"readOnlyHint"})` (empty set of required parameters).
   The existing tests in that file are "`tools/list` snapshot + error-code mapping" and **do not hit the network** (file header docstring);
   the shaping logic added in this ticket must be testable as a pure function, so extract item 3 into a module-level function (e.g. `_shape_overview(payload)`) and unit-test it.

### Contract

Tool inputs -> query parameters are **forwarded 1:1 under the same names**, with no renaming and no aliases. The return value is the upstream 200 JSON,
minus `debug`, possibly with two extra fields `breakdownReturned` / `breakdownTruncatedByToolOutput` (only when truncation occurs).
Errors always use this repo's existing error envelope (the classification at `api_client.py:62-64` + the shape of `_json.error_envelope`),
**without inventing a new error shape**.

### Non-functional

- **Multi-tenant isolation**: the tenant comes from the caller's token (`api_client.py:87` + the contextvar isolation in `server.py`),
  the wrapper **accepts no tenant parameter** and keeps no cache. When `sopId` falls outside the tenant the upstream naturally returns an empty range (as the ticket states).
- **Read-only**: `readOnlyHint=True`, and only one GET is sent, with no body.
- **Output budget**: see change list item 3. The cap comes from `_json.py:11`.
- **Timeout/retry**: keep the existing `AgentClient` behavior; not changed in this ticket.
- **No sensitive information in logs**: this ticket adds no logging; neither the token nor the response body is logged.

### Risks

- **R1 Truncation semantics with large `pageSize`.** Without item 3, we get "the model thinks it saw everything but did not" -
  worse than an error, because it is invisible. AC7 is the safeguard.
- **R2 Unit convention (OQ-1).** If the tool description says only USD, the agent's answer will not match the credits on the Usage page.
  This is explained in the description per the assumption, but it is a product-convention question, so it is safer to confirm it at grooming.
- **R3 AC5 depends on the environment (OQ-3).** When `08745928` is not in the target deployment, `createdBy` / `createdAt` simply do not exist,
  and **no error is raised** - the response just lacks two fields. So acceptance of AC5 must first confirm the deployed version, or it will be misjudged as an implementation omission.

### Effort

About 0.5-1 person-day (including tests). The change is concentrated in one new file + one registration line + tests, with no cross-repo dependency.
