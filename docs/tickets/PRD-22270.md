## Requirement understanding

One line: Add one agent-callable tool named exactly `schedule_resume` to the platform's own system MCP (`mspbots-agent-mcp`, connector "mspbots-agent") that calls the PRD-20855 endpoint `POST /api/agents/:agentId/threads/:threadId/schedule-resume`, so an agent can pause its run until a time and be resumed.

Decisions the ticket already fixes: the tool is a thin wrapper shaped like `mspbotsagent_upsert_trigger`; the agent id and thread id come from the calling run and never from the model; the endpoint's answer is returned unchanged; endpoint errors (422 date with no time / beyond horizon, 429 cap reached, 403) reach the agent as readable tool errors; flags off gives a clear "not available" error; no change in `mb-platform-agent` or `mb-platform-aegra`.

## Current state (every claim carries path:line)

- The repo registers tools per module with `register(mcp, client_factory)`; each tool resolves the client from the request context and returns `NO_TOKEN` without one (`tools/triggers.py:14-42`, `tools/_common.py:3-7`). Every existing tool is named `mspbotsagent_*` (`tests/test_tools.py:21-97`); the test only checks the set of names, not the prefix (`tests/test_tools.py:99-103`).
- Credentials come from the request headers through `GatewayTokenMiddleware` into a per-request contextvar of four values (`server.py:19-23,48-100`). Only `X-Channel-Run-Origin` is read today; the thread and agent ids are not.
- mb-platform-agentos sends `X-Channel-Thread-Id` (always) and `X-Channel-Agent-Id` (when the run knows the agent) on every MCP tool call, and its README says a server acting on the platform agent should take the agent id from that header and not from a tool argument (`mb-platform-agentos@release agentos/tools/mcp.py:37-38,118-139`, `README.md:670-680`). `X-Channel-Run-Origin` rides in the same dict and already reaches this server (PRD-21389), so the two ids reach it the same way.
- `AgentClient.post` sends `X-API-Key` and `X_Tenant_ID`, forwards `X-Run-Origin`, retries 429/5xx up to three times with backoff, and raises `AgentError(status, message)` (`api_client.py:79-211`). `AgentError.to_envelope()` maps 403 to `unauthorized`, 404 to `not_found`, 422 to `invalid_argument`, 429 to `rate_limited` with `retryable=true` (`api_client.py:33-58`).

A success is `{success:true,data:{wait_id,status,resume_at,timezone,late_by_seconds,...}}`.

## Product design

### Goals
1. An agent connected to the `mspbots-agent` connector sees a tool named exactly `schedule_resume` in its tool list, with the parameters below.
2. Calling it creates (or, with the same `key`, moves) a scheduled wait on the calling run's own thread, for the calling run's own agent; the model never supplies either id.
3. The platform's answer comes back unchanged; its refusals come back as readable errors; nothing is scheduled when it refuses.

### Non-goals
- No change in `mb-platform-agent`, `mb-platform-aegra` or `mb-platform-agentos`; no new endpoint.
- No list / cancel / run-now tool (the UI and PRD-20855 own those).
- No date parsing, horizon or cap logic in the wrapper: the endpoint owns all of it.
- The pause itself is the platform's `interruptOn` entry for the tool name `schedule_resume`; the wrapper does not pause anything.

### Tool contract (named parameters)
| Parameter | Type | Required | Meaning |
|---|---|---|---|
| `key` | string | yes | Identifies this wait within the run; the same key again moves the wait |
| `reason` | string | yes | Why the run waits (shown on the run) |
| `resume_at` | string | one of the two | ISO 8601 instant with offset, or local date-time with `timezone` |
| `resume_in` | string | one of the two | Duration from now, for example `3m`, `2h`, `14d` (the endpoint decides the accepted forms) |
| `timezone` | string | no | IANA timezone |
| `wake_on` | list of `note`/`updated`/`closed`/`deleted` | no | Ticket events that wake the run early |
| `cancel_on` | list of `closed`/`deleted` | no | Ticket events that cancel the wait |
| `ticket` | object `{integration, id}` | no | The ticket the events refer to |

Exactly one of `resume_at` / `resume_in` is required: giving both or neither is refused before any request is sent. Agent id and thread id are not parameters.

### Acceptance criteria
- AC1 (DW1): Given an agent on INT with the mspbots-agent connector, When it lists its tools, Then it sees `schedule_resume` with the parameters above and no `agent_id` / `thread_id` parameter.
- AC2 (DW2): Given `SCHEDULE_RESUME_CORE` on and the tool paused by `interruptOn`, When the agent calls `schedule_resume` with `resume_in` = 3 minutes, Then the run shows "Scheduled" and resumes about 3 minutes later in the same run.
- AC3 (DW3): Given a pending wait, When the agent calls `schedule_resume` again with the same `key`, Then the wait moves to the new time and no second wait exists.
- AC4 (DW4): Given a date with no time, a time beyond the horizon, or the cap reached, When the agent calls the tool, Then it receives a readable error that says what was refused and why, and nothing is scheduled.
- AC5 (DW5): Given the `SCHEDULE_RESUME_*` flags off, When the agent calls the tool, Then it receives a clear "not available" error and the run is not left paused.
- AC6 (DW1, DW4): Given a call with both or neither of `resume_at` / `resume_in`, or no `key`, or a call that has no run thread or agent id in its headers, When the tool is called, Then a readable error comes back without any request to the platform.

### Open questions
1. Not blocking, assumption stated: the pause of PRD-20855 is the platform's `interruptOn` entry for `schedule_resume`; the platform design says the parked run is resumed by the platform with the payload as the tool result. Whether the harness reaches the wrapper before or after the pause is PRD-20855 / agentos behaviour, outside this repo. This design assumes the wrapper is an ordinary tool called by the harness. If INT shows the call never reaches the wrapper before the run pauses, that is a follow-up in PRD-20855 / mb-platform-agentos; this card's cases TC8 and TC9 are the ones that would show it.
2. Not blocking, assumption stated: the tool takes flat named parameters, which is how every sibling tool is shaped; "one options object" in the ticket is read as "named parameters", not a single wrapping object.
3. Not blocking: `reason` is required here (the ticket lists it with `key`); the endpoint itself only requires `key`.

## Technical design

### Change list
- `src/mspbots_agent_mcp/server.py` [change] - read `x-channel-thread-id` and `x-channel-agent-id` in `GatewayTokenMiddleware` into a second contextvar `_caller_var` (default `None`; both optional, so a caller without them is never 401'd), and add `get_caller_from_context()` returning `(thread_id, agent_id)`; register the new module (`schedule.register(registrar, client_factory, caller_factory)`); add one short sentence to the server `instructions` (must stay within the 1500-char limit asserted at `tests/test_tools.py:219-222`).
- `src/mspbots_agent_mcp/tools/schedule.py` [new, about 90 lines] - one `@mcp.tool(annotations=ToolAnnotations(idempotentHint=True))` named `schedule_resume` (function name is the tool name, no `mspbotsagent_` prefix: the ticket requires the exact name for `interruptOn`). Steps: client from context else `NO_TOKEN`; caller ids from context else a `not_configured` error ("schedule_resume can only be called from inside an agent run"); local check of one-of `resume_at`/`resume_in` and non-empty `key`/`reason`; build the body with only the given fields; `client.post(f"/api/agents/{agent_id}/threads/{thread_id}/schedule-resume", body, retries=0)`; return `dump_json(result)` unchanged. `retries=0` because a 429 here is "cap reached" and waiting does not help; the key makes a repeat call safe, so the model can simply call again after a 5xx.
- `src/mspbots_agent_mcp/tools/schedule.py` error mapping - on `AgentError`: status 404 with message exactly `Not found` (the endpoint's feature-flag-off answer; "Agent not found" is a different message) becomes `error_envelope("not_available", "schedule_resume is not available on this platform yet (the scheduled-actions feature is off).", False)`; 429 becomes `error_envelope("limit_reached", <endpoint message>, False)` (not retryable); every other status uses `e.to_envelope()` so 422 / 403 messages reach the agent as they are.
- `tests/test_tools.py` [change] - add `schedule_resume` to `EXPECTED_TOOLS` (required `{key, reason}`, hint `idempotentHint`).
- `tests/test_schedule_resume.py` [new] - stub client and context, see Test cases.
- `README.md` [change] - tools table row, and one bullet in "When would you use this".
- `docs/modules/mcp-tools.md` [not written by design] - the dev leg updates it after delivery.

### Contract
Request to the platform: `POST /apps/mb-platform-agent/api/agents/<agentId>/threads/<threadId>/schedule-resume` with headers as for every call (`X-API-Key`, `X_Tenant_ID`, `X-Run-Origin` when present) and body, for example:
```
{"resume_in":"3m","key":"offboard-jdoe","reason":"Last working day","wake_on":["note","updated"],"cancel_on":["closed"],"ticket":{"integration":"halopsa","id":"1234"}}
```
Answer returned to the agent: the platform body unchanged, for example `{"success":true,"data":{"wait_id":"...","status":"pending","resume_at":"2026-11-17T10:03:00.000Z","timezone":"UTC","late_by_seconds":0}}`. Errors: `{"error":{"code":"invalid_argument","message":"...","retryable":false}}` for 422, `unauthorized` for 403, `limit_reached` for 429, `not_available` for the flag-off 404.

### Options
- Agent id: a hidden `agent_id` argument filled by agentos (as agentos does for tools that declare it) versus the `X-Channel-Agent-Id` header. The header is chosen: the thread id has no argument route at all (only the header), so one mechanism for both ids is simpler, and agentos documents the header as the intended source.
- Validation: local checks only for what makes a request meaningless (one-of time, `key`, `reason`, ids); everything about dates, horizon and caps stays in the endpoint so the two can never disagree.

### Reuse and cleanup
- Reuse: `AgentClient.post`, `AgentError.to_envelope`, `error_envelope`, `dump_json`, `NO_TOKEN`, the `register(mcp, client_factory)` shape, the `_DedentedDocs` registrar. No new dependency.
- New signatures: `schedule.register(mcp, client_factory, caller_factory)`; `get_caller_from_context() -> tuple[str, str] | None`.
- Cleanup in touched code: none needed. Suggest separate tickets: none.

### Non-functional
- Idempotency: the endpoint upserts by (thread, key), so a repeated call moves rather than adds; the tool is marked `idempotentHint`.
- Security / multi-tenancy: the ids are taken from headers set by the harness, never from the model, so a model cannot attach a wait to another agent or thread; the platform still checks agent access (403) and its own thread-ownership rules; no credential is logged or returned.
- Compatibility: the two new headers are optional; callers that send neither are unchanged and only `schedule_resume` refuses them. Release order: no dependency (single repo; the tool only works once PRD-20855's endpoint is deployed with `SCHEDULE_RESUME_CORE` on, and says so when it is not).
- Observability: none added.
- Description budget: the tool description stays within 500 characters and a first line of at most 100, as the snapshot test requires.

### Testing strategy and regression surface
Unit tests with a stub client and stubbed caller context; one middleware test through the ASGI app for the two headers; the tool-list snapshot. Regression surface: the middleware (header parsing), the tool list and server instructions. Run `uv run pytest` (baseline on main: 86 passed, 8 skipped).

Main uncertainty: the harness-side pause ordering (Open question 1), outside this repo

### Risks
- The wrapper works end to end only with PRD-20855 deployed and its flags on; with them off it says "not available".
- If agentos does not send `X-Channel-Agent-Id` for a run (the header is omitted when the assistant config has no agent id), the tool refuses with a clear error rather than guessing.
