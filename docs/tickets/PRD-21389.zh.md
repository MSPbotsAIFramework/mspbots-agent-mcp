## 需求理解

一句话：Don 希望生产/触发类的 agent 运行不能改动该 agent 自己的配置（连接器工具开关、权限与审批规则、trigger、自评规则、SOP/skill 内容、模型设置）——只有 agent 自己的聊天（builder/维护场景）能改，且按 Micus 2026-10-26 的决定，"Run now" / "Run for…" 与公共 API 也算生产运行。

Don（提单人）观察到现在每个 agent 都挂了系统 MCP `mspbots-agent`，暴露出诸如 `upsert_agent_permissions` 这类平台管理工具，据此推断一个正在运行的 agent 可以用它们来破坏自己的安全控制（例如重新打开一个刚被人关掉的工具）。PRD-17198（2026-09-03 已关闭）不覆盖这个需求：它的前提——"没有任何 agent 的工具列表里有平台管理 API"——现在已经不成立。

工单上已记录的决定（Micus，2026-10-26）：(a) 对每个 agent 默认开启，v1 不提供按 agent/按 trigger 的开关；(b) "Run now" 与 "Run for…" 算生产运行，同样要被拒绝；只有 agent 自己的聊天能改配置。Scope 和 Done when 对开发来说已经定稿（不再经产品复审）。

## 产品设计

### 目标 / 非目标

**目标**
- 生产/触发类的 agent 运行不能改动自己的配置：连接器工具开关、权限、审批规则、trigger、自评规则、SOP/skill 内容、模型设置。
- 被拒绝的尝试返回清晰、具体的工具错误，且配置保持不变。
- agent 自己的聊天（交互式聊天 + SOP Author builder/维护会话）不受影响——owner/admin 在那里仍能改动以上全部内容。

**非目标（v1，按工单原话）**
- 不提供按 agent 或按 trigger 的开关——规则对所有 agent 始终开启。
- 不做可见的"build vs 生产"模式（计划留到以后，和 Epic PRD-20763 的按客户 draft/live 一起做）。
- 把聊天本身限制给管理员，不在本单范围内。
- `mspbotsagent_run_trigger`（执行一个已存在的 trigger）不受限制——它是一个动作，不是配置改动。

### 验收标准 AC1..AC6

- **AC1** —— 在表单或定时触发的运行里，连接器工具开关路由（`set_connector_tools` / `PUT /api/agents/:id/connectors/:cid/tools`）被拒绝，agent 的工具开关事后保持不变。（Given/When/Then：给定一次 task-origin 的运行，当有调用试图切换某个连接器的工具开关时，该调用被拒绝，`.mcp.json` 里的 `allowedTools`/`disabledTools` 保持不变。）
- **AC2** —— `upsert_agent_permissions` 在这类运行里同样被拒绝。
- **AC3** —— 范围内的其它每个类别（trigger、自评规则、SOP/skill 内容、模型设置）至少有一次被拒绝的调用得到验证。`run_trigger` 明确验证为**不**被拒绝（它是执行，不是配置）。
- **AC4** —— 一个被人关掉的工具在下一次运行里保持关闭状态，即使有一次触发运行试图把它打开。
- **AC5** —— 在 agent 自己的聊天（交互式）以及 SOP Author builder/维护会话里，owner/admin 仍能改动上述所有设置——不受本次改动影响。
- **AC6** —— 每一次被拒绝的尝试都会出现在该次运行的历史里（作为运行/会话记录里的一条工具调用错误）。

### Open Questions

- **OQ1（不阻塞，已按假设继续）：** `RunOrigin` 声明了 `"test"` 和 `"compact"`，但在本仓当前读到的 sha 上没有找到任何一处真正设置过它们的调用点（`"compact"` 只在客户端设置过一次，`components/assistant-ui/aegra/compact.ts:23`，用于 LangGraph 自己的历史压缩调用——不是人发起的运行）。假设：只有 `origin ∈ {chat, build}` 豁免；`test`/`compact`/任何未识别的值一律按非豁免处理（默认拒绝）。如果以后有"测试这个 agent"的功能从 builder 内部设置 `origin: "test"`，到时候再把它加进豁免集合。

## 技术设计

### 结论

把拒绝逻辑放在 **`mb-platform-agent` 的后端路由内部**执行（而不是 `mb-platform-agentos` 的工具调用层），依据一个新信号——运行的 `origin`（本来就已经被记录下来，只是在离开 `mb-platform-agent` 之前就被丢掉了）——经由 `mb-platform-agentos` 和 `mspbots-agent-mcp` 以一个转发的 header 传递过去。不改动任何现有字段（`source`、`run_source`）的语义。

### 现有实现定位

每条路由、文件、行号见上方「现状」各表。三个仓库各自角色的小结见「多仓联动」。

### 方案选型

**方案 A——复用现有的粗粒度 `run_source`（"task"/"chat"），修正两个打错标的发起点。** `mb-platform-agentos` 的 `graph.py:39`（`_writable`）已经是这么读 `run_source` 的，所以这会是最小的改动：把 `triggerRun`（route.ts:1254）和 `agent-invoke.ts:66` 的 `source: "chat"` 改成 `source: "task"`，然后在 `run_source == "task"` 上拦。
**否决理由**：`source` 已经有两个与本单无关的独立消费方，改动会带来副作用——`listAllRuns` 的"所有运行"/收件箱页面按 `source: "task"` 过滤（`route.ts:1739,1767`），"Run now"/"Run for…"/公共 API 的运行会因此开始出现在那个页面里，而它们今天不会；`_writable` 本身也会让这些运行的文件系统新增变为只读。这两点很可能都是*合理*的（它们确实不是聊天）,但都是本单声明范围之外的、用户可见的副作用，而且本单自己写的任何测试都不会去覆盖一个本单根本没打算碰的过滤器上的回归。

**方案 B——采用。** 把本来就更细的 `origin` 字段作为一条新增的、独立于 `source`/`run_source` 的信号传递下去：
1. `mb-platform-agent` 的 `runContext()` 额外吐出 `run_origin`（取自本来就已经记在运行 metadata 里的 `origin`）——一行新增，`source`/`run_source` 不动。
2. `mb-platform-agentos` 在 `make_graph()` 里读 `configurable.run_origin`，往下传到构建 MCP 工具调用的地方——那里本来就已经为另一个目的（`agent_id`/`thread_id` 自动回填，见下）注入每次调用的 header，这次只是多加第三个 header。
3. `mspbots-agent-mcp` 读这一个多出来的 header，原样转发给 `mb-platform-agent`。
4. `mb-platform-agent` 的改配置路由校验它。

对 `source`/`run_source` 的消费方零副作用；`mb-platform-agentos` 和 `mspbots-agent-mcp` 各自的改动量约 2 个文件，两边都是在扩展一个已有的、直接对应的既有模式（`_caller` 拦截器；三个 header 的鉴权中间件），而不是发明一个新机制。

### 改动清单

**`mb-platform-agent`**
- `service/aegra/metadata.ts:37-39`（`runContext`）—— 在返回对象里加一行 `run_origin: typeof metadata?.origin === "string" ? metadata.origin : ""`。`run_source` 不动。
- 新增共用闸门，例如 `service/aegra/run-origin-guard.ts`（新文件）—— `requireNonProductionOrigin(c: Context): Response | null`。读 `c.req.header("x-run-origin")`；如果这次请求**不是** api-key 鉴权（正常会话鉴权——`requireAgentAccess`/`getMe` 那条路径），一律返回 `null`（不拦——人走界面永远不受影响）。如果是 api-key 鉴权：header 恰好是 `"chat"` 或 `"build"` 时返回 `null`；否则（缺失，或任何其它值）返回一个 `403` 信封 `{ success: false, error: "This agent's configuration can't be changed during a triggered run" }`。
- 依次在以下路由开头调用这个闸门：`app.put("/api/agents/:id/connectors/:cid/tools", ...)`（`service/capability/route.ts:328`）、`app.put("/api/agents/:id", ...)`（`service/agent/route.ts:2363`——因为权限/自评/审批/模型共用这同一条路由，这里一处就覆盖了全部）、`app.post("/api/tasks", ...)` / `app.put("/api/tasks/:taskId", ...)` / `app.delete("/api/tasks/:taskId", ...)`（`service/task/route.ts`——这三处注册的准确行号由开发棒在同一个文件里确认，就在 `taskMetadata` 附近）、五个 `PUT /api/agents/:id/sop-author/{name,source,purpose,data-sources-list,procedure}` 路由外加 section-visibility/clear（`service/capability/route.ts`，与 `:239` 处的 `createSkill` 同一片区域）、以及 `POST /api/agents/:id/skills/create` / `PUT .../files` / `DELETE .../skills`（`service/capability/route.ts`）。**刻意不拦**：`POST /api/tasks/:taskId/run`（`mspbotsagent_run_trigger`——执行，不改配置）。
- `service/capability/route.ts`、`service/agent/route.ts`、`service/task/route.ts`——每处加一次闸门调用，沿用这几个文件里已有的 `requireAgentAccess`/`requireDev` 提前返回的写法。

**`mb-platform-agentos`**
- `agentos/graph.py:58-80`（`make_graph`）—— 读 `run_origin = str(options.get("run_origin") or "").strip()`；传进 `mcp.load(assistant, agent_id, run_origin)`。
- `agentos/tools/mcp.py`—— 把 `load(assistant, agent_id="", run_origin="")`（`:361`）、`tools(servers, agent_id="", run_origin="")`（`:323`）、`_caller(agent_id, run_origin, owned)`（`:118-139`）的签名都扩展一下，把这个值带下去；在现有的 `CALLER_THREAD_HEADER`/`CALLER_AGENT_HEADER` 常量（`:37-38`）旁边加一个 `RUN_ORIGIN_HEADER = "X-Channel-Run-Origin"`，在 `:132-136` 构建 `caller` dict 的地方，`run_origin` 非空时把它也加进去。

**`mspbots-agent-mcp`**
- `src/mspbots_agent_mcp/server.py`（`:50-67` 附近那段读 `x-msp-token`/`x-msp-tenant-id`/`x-msp-host` 的中间件）—— 同时读 `x-channel-run-origin`（可选；缺失则视为空字符串，后端闸门会把空字符串按非豁免处理，即默认拒绝），存进和另外三个值同一个请求级 contextvar。

### 数据与接口契约

- 新 header，agentos → `mspbots-agent-mcp`：`X-Channel-Run-Origin: <origin>`（与该仓自己的 `X-Channel-*` 命名习惯一致）。
- 新 header，`mspbots-agent-mcp` → `mb-platform-agent`：`X-Run-Origin: <origin>`（与 `mb-platform-agent` 自己这类内部信号的命名习惯一致）。
- 豁免值：`chat`、`build`。其它一切（含缺失）⇒ 在调用方是 api-key 鉴权时一律拒绝。
- 拒绝响应：`403`，JSON 信封 `{ "success": false, "error": "This agent's configuration can't be changed during a triggered run" }`——这个原样字符串会被 `AgentClient` 的 `AgentError.to_envelope()`（`mspbots-agent-mcp/src/mspbots_agent_mcp/api_client.py:56-67`）原样带回去，作为该次 MCP 工具调用的错误结果，MCP 层不需要新写任何代码就满足了"被拒绝的调用返回清晰的工具错误"。
- 无 DB schema 改动，无迁移。

### 关键流程时序

```
schedule/event/webhook/Run-now/公共 API 发起一次运行
  → mb-platform-agent 打 origin 标（cron/manual/event/api——都已经是对的，见「现状」表）
  → runMetadata() 把它记下来；runContext() 现在也吐出 run_origin（新增）
  → Aegra 的 configurable.run_origin 到达 mb-platform-agentos 的 make_graph()
  → agentos 把 run_origin 传进 mcp.load() → tools() → _caller()
  → agentos 发出的每一次 MCP 工具调用现在都带着 X-Channel-Run-Origin
  → mspbots-agent-mcp 的 server.py 读到它，转发成 X-Run-Origin
  → mb-platform-agent 的闸门看到某条改配置路由上、api-key 调用的 X-Run-Origin
    不是 chat/build → 403，配置不变
  → MCP 工具调用返回一个错误信封 → 在该次运行的记录里可见（AC6）
```

聊天/builder 路径：完全一样，只是 `origin` 全程是 `chat`/`build`，所以闸门全程走"返回 null"这条路径，今天的每一次写入都照常生效（AC5）。

### 非功能

- **多租户**：新 header 只带 `origin`，不带任何租户/身份信息；既有的按租户隔离（`requireAgentAccess`、schema-per-tenant 的 DB 访问）先于本闸门执行，不受影响——见 TC14。不引入新的跨租户面。
- **默认拒绝（fail-closed）的设计取向**：api-key 调用上缺失或无法识别的 `X-Run-Origin` 一律按生产处理（拒绝），而不是放行——见 TC15。这是唯一值得单独点名的非功能性质，因为它带出了下一条（上线顺序风险）。
- **上线顺序（硬性要求，不是建议）**：因为这个 header 是默认拒绝的，如果 `mb-platform-agent` 的闸门先于 `mb-platform-agentos` 和 `mspbots-agent-mcp` 都已经在发这个 header 之前就上线，**所有** api-key 鉴权的 agent 自我配置调用——包括 agent 自己聊天/builder 会话里那些合法的调用——都会开始被拒绝（因为 header 根本不存在）。上线顺序：(1) 先上 `mspbots-agent-mcp` + `mb-platform-agentos` 的改动，通过日志确认至少一次真实的聊天/builder 会话和一次真实的触发运行，`X-Run-Origin` 都带着正确的值到达；(2) 确认之后再上 `mb-platform-agent` 的闸门。这是给开发棒"上线与回滚"一节的明确指令，不是可选的先后顺序建议。
- **并发**：不引入新的写路径；闸门是在既有处理函数执行之前做一次纯读取判断再决定要不要拒绝，不改变任何既有的加锁/部分写行为（例如 `mspbots-agent-mcp/README.md` 里"不要对同一 agent 并发写"那条提示）。
- **可观测性**：被拒绝这件事本身因为会出现在运行历史里（AC6，工具调用错误）而天然可见，所以严格来说不需要新增日志，但建议开发棒在拒绝发生时考虑加一行日志（agent id、路由、origin）便于排查/监控——不是硬性要求。

- 回滚就是三个仓库各自改动的直接 revert；没有写过任何数据，不需要向后迁移。
