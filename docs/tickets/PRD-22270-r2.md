## Rework triage

Type: implementation error. The description did not change and no human comment asks for different behaviour; the INT QA run found that the delivered code does not meet round-1 AC4 and AC5 (DW4, DW5).

Evidence (QA-NIGHT, INT v20261117.0548): with `SCHEDULE_RESUME_CORE` off the endpoint answers 404 `{"success":false,"error":"Not found"}`; the tool returned code `not_found` with "unknown error" instead of `not_available`. Cause: `AgentClient._handle` reads the error text only from the body's `message` (`api_client.py:206`), but the PRD-20855 endpoints put it in `error`, so every refusal (404, 422, 429, 403) degrades to "unknown error" and the `Not found` -> `not_available` branch in `schedule.py` never matches. Round-1 tests missed it because TC4/TC5 stub by raising `AgentError` directly and bypass `_handle`.

Changed this round: no product-design change (AC1-AC6 as round 1); technical design gets one change (below); test cases: TC1-TC9 kept unchanged, TC10 and TC11 added. Nothing removed or reworded.

## Product design

Unchanged. AC4 and AC5 of round 1 already require "a readable error that says what was refused and why" and "a clear not available error"; this round makes the delivered tool meet them.

Not blocking, noted for PRD-20855 (assumption stated, no change here): QA observed that in a real run the agent sees the tool as `mspbots-agent_schedule_resume` (connector prefix), not the bare `schedule_resume`. The tool's own name stays exactly `schedule_resume` as the ticket requires; whether PRD-20855's `interruptOn` match handles the prefixed name is a PRD-20855 / agentos check, outside this repo and outside this card's Done when.

## Technical design

### Change list
- `src/mspbots_agent_mcp/api_client.py` [change] - in `AgentClient._handle`, take the error text from the body field `error` when it is a non-empty string, else fall back to `message` (existing behaviour for the other platform endpoints), else "unknown error". When `error` is an object with a `message`, use that. Keep the `errors` details suffix. No other behaviour change (success path, empty body, non-JSON body untouched).
- `tests/test_schedule_resume.py` [change] - add TC10 and TC11: build real `httpx.Response` objects with the four real endpoint bodies and run them through the real `AgentClient._handle` (or a client on `httpx.MockTransport`), then through the tool, asserting the final envelope. Do not stub `AgentError`.
- `tests/test_api_client.py` [change or new if absent] - `_handle` unit cases: `error` string, `message` string, both present (`error` wins), neither (unknown error), `errors` suffix kept.
- `schedule.py` needs no change: its `Not found` match is correct once `_handle` delivers the text. If the review finds the match should be case/whitespace tolerant, that is the developer's call within TC10.

### Contract
Endpoint error bodies (from the PRD-20855 design): `{"success":false,"error":"<text>"}` for 404 / 422 / 429 / 403. After the fix the tool returns, for example, `{"error":{"code":"not_available","message":"schedule_resume is not available on this platform yet (the scheduled-actions feature is off).","retryable":false}}` for the flag-off 404 and the endpoint text under `invalid_argument` / `unauthorized` / `limit_reached` for the others.

### Reuse and cleanup
Reuse the existing `_handle`; no new dependency. Cleanup: none beyond the fix. Suggest separate tickets: none.

### Non-functional
Compatibility: other tools read `message` and keep working (fallback, covered by TC11). Security: error text is the platform's own message, no credential involved. Release order: no dependency.

### Effort & breakdown
Story points: 0.5
Tier: 0.5 - single small fix in one repo (from logged time: 0.37 h / 7)
Considerations: 1 repo, one function, no data change, no UI, new tests only for two bodies shapes
Order: 1) `_handle` fix 2) TC10/TC11 and `_handle` unit tests, run the full suite

### Risks
Other endpoints that put text in `error` as an object: handled by the object branch. Remaining INT check after release: TC8/TC9 still need PRD-20855 with its flags on.
