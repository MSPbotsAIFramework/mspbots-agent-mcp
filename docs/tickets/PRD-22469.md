## Requirement understanding

One line: Make the agent-builder MCP server tell the AI that builds an agent to end every agent's instructions it uploads or updates with a "How to write your final reply" section holding the given "output for people" rule word for word, by adding the rule to the server instructions and one pointing sentence to the upload_agent and update_agent descriptions.

Decisions the ticket already fixes: wording only, no new tool or parameter; the MCP stores exactly the text the builder sends (no server-side insertion or rejection); the rule text lives in one place in the repo; only `mspbotsagent_upload_agent` (description and `prompt`) and `mspbotsagent_update_agent` (description and `instructions`) change, each by one sentence of at most 200 characters; the harness-side default for existing agents is PRD-22445.

## Current state (every claim carries path:line)

- The server instructions are one string passed to `FastMCP(instructions=...)`, 1462 characters today (`server.py:155-189`; measured on main 3b13393 with `len(create_mcp_server(Settings()).instructions)`). They describe concepts and tool groups and say upload creates an off draft only (`server.py:171-172`). They say nothing about how an agent's final reply must read.
- A test caps the instructions at 1500 characters (`tests/test_tools.py:230-233`). The rule alone is about 1.1 thousand characters, so this cap has to be raised in this change.
- `mspbotsagent_upload_agent` has a long docstring (778 chars) and a `prompt` parameter described as "System prompt / instructions." (`tools/agents.py:663`). `mspbotsagent_update_agent` has an 861-char docstring and an `instructions` parameter described as "The agent's full SOP / instructions text. REPLACES the current text." (`tools/agents.py:812-815,841-862`). Both are already on the long-description exception list of the 500-char budget test (`tests/test_tools.py:160-182`), so one more sentence breaks no budget.
- `update_agent` has a test that checks its description contains six phrases and its first line is at most 100 characters (`tests/test_tools.py:505-515`); appending a sentence at the end of the docstring keeps both true.
- The tools pass `prompt` / `instructions` to the platform unchanged (`tools/agents.py:867-868`; `prompt` for upload goes into the POST body as given). Nothing in the server edits the text.
- Descriptions are dedented by `_DedentedDocs` and a test checks `description == inspect.cleandoc(description)` (`server.py:121-147`, `tests/test_tools.py:210-227`); the new sentences must keep that.
- Reproduction: not applicable (feature, not a bug).

## Product design

### Goals
1. A client that connects receives, in the server instructions, one short paragraph for builders and then the rule: when you write or replace an agent's instructions, end them with a section headed "How to write your final reply", with the rule copied word for word.
2. The upload_agent and update_agent descriptions and their `prompt` / `instructions` parameters each carry one sentence (at most 200 characters) pointing at that section; when replacing instructions the builder keeps the section.
3. The rule text exists once in the repo; the server instructions and the tool sentences are built from that one place.
4. Nothing else changes: every other tool's name, description and parameters are identical; the MCP stores what it is sent.

### Non-goals
- No server-side insertion of the rule into a prompt and no check that rejects a prompt without it (a follow-up card decides after Done when 3 results).
- No change to agents that already exist, to the runtime harness (PRD-22445), the old UI "Create Agent" prompt, the FDE checklist or how Agent Hub renders markdown.
- No new tool, parameter or permission.

### The rule text (kept verbatim; the lead line plus eight points)

The ticket calls these "eight numbered points". The rule has a lead line and eight lines after it (start with one plain sentence; say what you changed; if something needs a person; lists in a table; never show null/JSON; use people's names; keep it short; raw data only when asked). They are not numbered in the text the card gives, and the spec check noted this. The design keeps the text exactly as the card gives it (no numbers added, since "word for word" is the requirement) and QA counts the eight lines after the lead line.

### Acceptance criteria
- AC1 (Done when 1): Given a client connects, When it reads the server instructions, Then they contain the lead line and all eight points in the card's order and wording, and a sentence telling the builder to copy the rule word for word as the last section, headed "How to write your final reply", of every agent's instructions it uploads or updates.
- AC2 (Done when 2): Given tools/list before and after, Then `mspbotsagent_upload_agent` and `mspbotsagent_update_agent` each have one new sentence of at most 200 characters in the description and one in the `prompt` / `instructions` parameter pointing at the section, every other tool is identical to before, and the existing tests pass.
- AC3 (Done when 3): Given three fresh Claude Code sessions connected only to the INT MCP, each asked to build and upload the ticket-list agent, Then in all three (read back with get_agent) the prompt ends with a "How to write your final reply" section holding all eight points; the agents are off.
- AC4 (Done when 4): Given one of those agents switched on and run on a pasted list of five tickets (two with no assignee, one with no due date), Then the final reply starts with one plain sentence stating the result, says "No changes made.", shows the tickets in a markdown table of at most 6 columns with empty assignee as "unassigned" or "—", and has no null, undefined, NaN, raw JSON, tool name or id; the agent is switched off afterwards.
- AC5 (Done when 5): Given Claude Code asks to change one of those agents ("Also tell me which ticket is the oldest."), Then the saved instructions contain the new request and still end with the section and all eight points (needs PRD-22150 on INT).
- AC6 (Done when 6): Given an agent uploaded directly through the tool with a prompt that has no such section, Then the stored prompt is exactly the text sent; and an agent that existed before the release gives an identical get_agent answer before and after.

### Open questions
1. Is a roughly 1.4-thousand-character addition to the server instructions acceptable to the connector owners (Leo / August)? Not blocking. Assumed yes, as the card says; the 200-character limit on the tool sentences keeps the descriptions small.
2. The card says PRD-22445 adds the same rule to existing agents; the spec check found no final-reply rule in PRD-22445's scope. Not blocking and not ours: this card does not depend on it.

## Tech design

### Conclusion
Add one small module `src/mspbots_agent_mcp/final_reply_rule.py` that holds the rule text and the pointing sentences as constants, and use them in `server.py` (instructions) and `tools/agents.py` (two descriptions and two parameters). Raise the instructions length cap in the existing test. Add one test file. No change to runtime behaviour: the strings are static.

### Where the current implementation lives
Instructions: `server.py:155-189`. upload_agent: `tools/agents.py:659-720` (docstring and `prompt` Field at `:663`). update_agent: `tools/agents.py:809-862` (docstring, `instructions` Field at `:812-815`).

### Option analysis
- A (chosen): constants module imported by both places. One place for the rule, the tool sentences cannot drift (the ticket requires this). Python only, no new dependency.
- B: put the rule in a text file read at start-up. Rejected: adds file packaging (the Dockerfile and wheel would have to include it) and a runtime read for a static string.
- C: write the rule inline in `server.py` and copy the sentence into the two tools. Rejected: this is the drift the ticket forbids.

### Change list
- `src/mspbots_agent_mcp/final_reply_rule.py` (new): `FINAL_REPLY_HEADING = "How to write your final reply"`; `FINAL_REPLY_RULE` (lead line plus eight lines joined by newlines, exactly the card's text); `BUILDER_PARAGRAPH` (the sentence to the builder, ending with the rule); `UPLOAD_DESCRIPTION_SENTENCE`, `UPDATE_DESCRIPTION_SENTENCE`, `PROMPT_PARAM_SENTENCE`, `INSTRUCTIONS_PARAM_SENTENCE`, each at most 200 characters and each naming the heading.
- `src/mspbots_agent_mcp/server.py`: append `"\n\n" + BUILDER_PARAGRAPH` to the instructions string.
- `src/mspbots_agent_mcp/tools/agents.py`: upload_agent: the `prompt` Field description gains `PROMPT_PARAM_SENTENCE`; the docstring gains `UPLOAD_DESCRIPTION_SENTENCE` as its last paragraph (a docstring cannot hold a constant, so set the description from the constant by assigning `fn.__doc__` before registration, or pass `description=` to `@mcp.tool(...)`; the implementation picks the one that keeps the existing dedent test green). update_agent: same for `instructions` and its docstring.
- `tests/test_tools.py`: raise the instructions cap from 1500 to 3200 characters (rule 1.1 thousand + paragraph about 0.3 thousand + 1462 existing).
- `tests/test_final_reply_rule.py` (new): see Test strategy.
- `README.md`: one line in the upload_agent and update_agent rows noting the final-reply section guidance (docs only).

### Reuse & cleanup
- Reuses: `FastMCP(instructions=...)`, `_DedentedDocs`, the existing `Field(description=...)` pattern, the existing tools/list test helpers in `tests/test_tools.py`. No new dependency.
- Signatures: no tool, parameter, type or default changes; only description strings.
- Cleanup in touched code: none needed. The commented NOTE blocks at the end of the instructions string in `server.py:173-185` are not removed (they document hidden tools; unrelated to this card). Follow-ups to suggest as separate tickets: a server-side check if Done when 3 shows builders skipping the rule (the card already says so).

### Data & API contract
No API, DB or header change. tools/list changes only in two descriptions and two parameter descriptions; initialize's `instructions` field gains the paragraph and rule. Example of the new tail of the instructions:

```
When you write or replace an agent's instructions, end them with a section headed "How to write your final reply" and copy the rule below into it word for word, as the last section.

Write your final reply for a person, not for a program.
Start with one plain sentence: ...
...
```

### Key flow / sequence
Client connects, reads `instructions`, builds the agent, calls upload_agent with a prompt that ends with the section; or reads the update_agent description and keeps the section when replacing. The server forwards the text unchanged.

### Non-functional
- Idempotency and concurrency: not affected, static strings.
- Performance: instructions grow by about 1.4 thousand characters on every connection; the tool sentences add under 800 characters in total.
- Security and tenant isolation: none; no data, header or permission involved. The MCP still adds nothing to a prompt, so a builder cannot be tricked into storing text it did not send.
- Logging: none.

### Rollout & rollback
One connector release (INT first). Rollback is a revert of the commit. No migration. Release order: any.

### Test strategy
Auto, in `tests/test_final_reply_rule.py` and `tests/test_tools.py` (no network):
- the instructions contain `FINAL_REPLY_RULE` exactly, and the rule equals a literal copy of the card's text pinned in the test (so an accidental edit of the constant is caught);
- every sentence constant is at most 200 characters and contains the heading; the description of each of the two tools ends with its sentence, and each of the two parameter descriptions contains its sentence;
- tools/list: the set of tools whose description or parameters differ from a pinned snapshot of main is exactly the two tools (the snapshot test already in `test_tools.py` is extended);
- upload_agent with a prompt that has no section sends the same prompt to the stub client (nothing added); update_agent likewise.
Manual on INT (Done when 3, 4, 5 and the INT half of 6): QA with Claude Code. Regression surface: the whole existing suite (`uv run pytest`), in particular the 500-char budget, dedent and update_agent phrase tests.
